## Reported symptom and source-confirmed cause

- User asked (including typos) for **ALL UNREAD messages received over the previous 24 hours**, with 30+ results possible. Agent instead described unrelated Oct 13 messages, then claimed there were no unread messages in the Oct 17–18 window without an authoritative live mailbox query.
- `apps/web/src/app/api/chat/stream/route.ts:loadEmailContext` used a **fixed LIMIT 20**, fallback **seven-day** date range, drafts-first sorting, **no unread filter**, and fuzzy search terms extracted from **recent assistant messages** combined with the current user prompt. The LLM could therefore be given incomplete/irrelevant mail and hallucinate exact claims. This old 20-row fallback remains for unrelated unspecific legacy prompts; the exact rolling-window path now bypasses it.
- The existing email tool `email.search` supports `date_from` and `unread_only` but has a bounded page limit and optional cursor; no server guarantee every page was fetched before a broad "all" claim. Prior approach "have the LLM infer scope, count and date from tool/context snippets" is not a reliable way to establish coverage.
- **Failed development approach caught by real tests:** the initial optional sender parser split `team@example.com` at the domain dot; first Node run 7/8 (sender filter test failed). Corrected punctuation handling, retained 24h-vs-sender distinction and added fail-closed unsupported-filter cases; retested 8/8 pass.

## Smallest corrective source slice

1. New pure `apps/web/src/lib/mail/rolling-summary.ts`: conservatively recognizes rolling 24h mail reports (including supplied typos like `Summery`, `Unreaded`, `Mesaages`), optional strict sender/topic filters, refuses unsupported/ambiguous filter wording, formats one listed record **per matching message** with subject/sender/mailbox/UTC date/short available text. Does not ask model to invent dates or to claim it saw messages that were not returned.
2. `apps/web/src/app/api/chat/stream/route.ts`: after normal session/organization/agent validation, **before** any old conversational-context gathering, requires authenticated `email.read` plus an enabled registered agent `email.search` or `email.messages.list` tool. Executes one parameterized, counted SQL query with the **same organization, agent and read-permitted mailbox bindings**, exact fixed rolling 24h UTC bounds, `is_read=false` when requested, excludes sent/draft, applies any explicitly parsed sender/subject/content filter, sorts newest first, and fetches at most 500 results. Fields from each stored email are byte-bounded. This is *locally synchronized* DB data only; no claim of fresh provider sync.
3. Returns **matched N / included M of N**, the time interval and every included message. At >500, explicitly says partial and how many were left out. At 0, says no matching synchronized rows — **never** asserts no new provider email. Persists user/report in the same authenticated conversation and delivers SSE `conversation`, `status`, `delta`, `done` with `source:local_mail_database` so clients see the source; chunks are **DB report bytes, not fabricated AI tokens**.
4. Additional safety: normal legacy `loadEmailContext` now only runs if the authenticated actor has `email.read`, preventing access by organization-only readers without that permission. Tool and approval handlers themselves were not changed; existing ISS-026 agent mailbox boundary maintained.
5. New Node regression `apps/web/tests/rolling-mail-summary.test.mjs` and Vitest SQL/auth-source contracts `apps/web/tests/chat-rolling-mail-summary.test.ts`.

## Prevention lesson and follow-up

- Never infer a dynamic time window, unread predicate or "ALL" from a prompt-only model fed an arbitrary capped 20-row sample. Translate supported scopes into **server-controlled, parameterized, tenant+agent-scoped, counted queries**, then explicitly report coverage and local-sync freshness.
- Avoid merging prior assistant text into a *new independent* broad mail scope; use history only for genuine follow-up resolution. Provider-side and local inbox counts can diverge while sync is delayed, so never claim provider completeness without sync evidence.
- Keep unsupported filters out of the broad direct-report path rather than broadening silently. No speculative LLM summary from unsanitized untrusted email content.
