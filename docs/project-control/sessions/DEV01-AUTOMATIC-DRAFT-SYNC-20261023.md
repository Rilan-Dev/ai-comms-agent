- **Owner symptom:** The live Drafts view lists saved draft subjects and includes separate `Sync provider draft` buttons. The core AI product should save drafted mail to a capable connected mailbox automatically without prompting users to press those buttons. Drafts list should be short, readable and emphasize items needing review. The agent should be able to find and update authorized drafts in chat. Owner has **not** authorized unattended sending; send approval remains mandatory.
- **Root cause:** `createLocalDraft` committed drafts locally with default `provider_draft_sync_status=local_only`. `updateLocalDraftForOrganization` unconditionally reset edits to `local_only`. The only queue admission was an explicit `POST /api/mail/drafts/sync` invoked by each visible UI button. The existing worker already safely handles queued remote creates/updates with `queued -> syncing` atomic claims, lease token, stale error quarantine and durable outcomes, and the worker startup already calls `startProviderDraftSyncLoop`. AI's `email.messages.list` had no `drafts_only` filter, so locally saved drafts could not be cleanly enumerated as pending work.
- **Implemented — transactional provider admission:** In `packages/db/src/email/repository.ts`, connected + `capabilities.drafts=true` marks a newly created draft `queued` **within the same transaction** as its local message/thread. Edits on safely settled/queued drafts queue an update; edits during `syncing` or with prior `error` are marked `error` and the old lease invalidated so an uncertain remote create is NOT blindly replayed. Send-action locks and organization/account predicates are preserved. `queueEligibleLocalDraftsForProviderSync` atomically promotes pre-existing `local_only` drafts for connected capable accounts with bounded `FOR UPDATE SKIP LOCKED`; it excludes pending/approved/executing send actions and any unknown-outcome/error syncs. No database schema or external send mutation.
- **Implemented — worker:** Exported the safe automatic admission in `packages/db/src/index.ts` and invoked it before `listDraftsPendingProviderSync` on the already registered five-second draft worker loop. Worker still requires configured encrypted provider credentials and honors `EMAIL_PROVIDER_DRAFT_SYNC_DISABLED`. A remote failure is a visible `error` requiring review, never background infinite retry that can duplicate provider drafts.
- **Implemented — end-user UX:** `DraftsClient` now shows concise draft count and optional pending/error counts; each row has subject, To/mailbox, one-line preview, simple `In mailbox drafts` / `Saving to mailbox…` / `Saved in app` / `Sync needs review` statuses; ordinary `Sync provider draft` buttons removed. `Retry sync` only appears on a failed/uncertain provider mutation, with explicit duplicate-warning confirmation. Existing review and local delete still available. Periodic status refresh uses monotonic request/revision and mutation-in-progress fencing to avoid stale GET reintroducing deleted drafts. Compose explains automatic saving and differentiates locally saved vs queued vs provider-synced. Deleting a local draft may not delete an already-saved provider copy, and the UI now says so rather than promising deletion everywhere.
- **Implemented — AI draft discovery:** `email.messages.list` and `email.search` now support `drafts_only=true`, enforced by existing tenant/account/agent/user email.read authorization. Draft-only results are ordered by most recently edited and include recipients and provider draft sync state. Existing authorized `email.draft.create/update/reply/forward` and approval request tools remain the write path. No model permission escalation, no automatic provider send or send approval creation.

- **Failure modes/avoidance:** Do not enqueue blindly if mailbox disconnected/unsupported. Do not enqueue a second creation after a timeout, interrupted worker, editing while in-flight or previous error. Never auto-send without the existing separate human approval. Do not delete remote drafts when user only chose local Delete. Preserve tenant account ownership and provider capability boundaries. Avoid a UI-only background POST since it misses AI-created drafts and offline clients; queue in durable DB writes instead.
