# EVENTS-AND-QUEUES.md

This document defines the queue/event architecture: RabbitMQ topology, queue contracts, idempotency, retries, and dead-letter handling. Per the master operating prompt §15, every asynchronous operation must define event schema, producer, consumer, idempotency key, retry policy, dead-letter behavior, correlation ID, observability, and failure handling.

This is a Phase 1 document. Concrete queue implementation (RabbitMQ exchanges, bindings, worker code) is Phase 4 (database foundation, which includes infra setup) and Phase 9 (sync workers).

---

## 1. Infrastructure

- **RabbitMQ** (CloudAMQP or self-hosted on the worker host — see ADR-007). Single broker, multiple queues.
- **Redis** (Upstash) for transient state: rate-limit counters, idempotency dedup windows (24h TTL), queue backoff state.
- **PostgreSQL** (Supabase) for authoritative state. The queue is **not** authoritative — losing a queue message is recoverable from PostgreSQL state (sync cursors, scheduled_jobs) and provider reconciliation.

The queue is async-only. Synchronous request/response (chat, voice turn) does not use the queue.

Each queue is durable, with a dead-letter exchange bound to `<queue>.dlq`. Messages are persistent. Consumers use manual ack — a message is acked only after successful processing; on failure, it's nack'd with requeue=false (goes to DLQ after retry budget exhausted).

## 3. Message envelope

Every message has the same envelope:

```typescript
type Message<T> = {
  // Identity
  id: string;                  // UUID, generated by producer
  correlation_id: string;      // links to request/conversation/agent
  idempotency_key: string;     // dedup key (see §4)

  // Routing
  routing_key: string;         // e.g., 'email.sync'
  producer: string;            // e.g., 'api.webhook.gmail'
  consumer: string;            // e.g., 'worker.email-sync'

  // Retry / DLQ
  attempt_count: number;       // 1 on first publish; incremented on retry
  max_attempts: number;        // default 5; per-queue override
  enqueued_at: string;         // ISO 8601
  available_at: string;        // ISO 8601 — when consumer may process (for backoff)

  // Payload
  payload: T;
};
```

---

## 4. Idempotency

Every consumer deduplicates by `idempotency_key`:

1. On dequeue, consumer checks Redis: `SETNX idempotency:{routing_key}:{idempotency_key} {message_id} EX 86400`
2. If `SETNX` returns 0 (key exists), the consumer checks the stored value:
   - If equal to current `message_id`: re-delivery of same message — ack without processing.
   - If different: a different message with the same idempotency key — log a warning, ack without processing (last-write-wins semantics).
3. If `SETNX` returns 1, the consumer processes the message. On success, the message is acked (the Redis key persists for 24h, preventing reprocessing). On failure, the Redis key is deleted, and the message is nack'd.

Idempotency keys are producer-defined and reflect the underlying event:

| Queue | Idempotency key |
|---|---|
| `email.sync` | `{account_id}:{history_id or cursor}` |
| `email.parse` | `{message_id}` |
| `email.index` | `{message_id}` |
| `email.attachments` | `{message_id}:{attachment_id}` |
| `email.classify` | `{message_id}` |
| `email.draft` | `{agent_id}:{draft_request_hash}` |
| `email.send` | `{draft_id}` or `{agent_id}:{send_request_hash}` |
| `email.action` | `{action_id}` |
| `whatsapp.inbound` | `{provider_event_id}` |
| `whatsapp.outbound` | `{agent_id}:{contact_phone}:{request_hash}` |
| `agent.schedule` | `{scheduled_job_id}:{fire_at}` |
| `agent.execute` | `{conversation_id}:{turn_id}` |
| `summary.generate` | `{agent_id}:{scope}:{period_start}:{period_end}` |
| `embedding.generate` | `{source_type}:{source_id}:{model}` |
| `voice.telemetry` | `{voice_session_id}:{turn_id}:{stage}` |
| `audit.persist` | `{audit_event_id}` |

## 5. Retry policy

- **Default**: 5 attempts, exponential backoff with jitter. Delays: 10s, 30s, 90s, 270s, 810s (~20 min total).
- **Backoff**: producer sets `available_at` on retry (consumer does not requeue immediately; instead, it nack's with requeue=false and re-publishes with a delayed `available_at` using the rabbitmq-delayed-message-exchange plugin, or a delayed queue per backoff tier).
- **Per-queue overrides**: some queues have different retry budgets (e.g., `voice.telemetry` is best-effort: 2 attempts only; `audit.persist` is critical: 10 attempts).

After `max_attempts` is exhausted, the message is nack'd with requeue=false and the dead-letter exchange routes it to `<queue>.dlq`.

---

## 6. Dead-letter queue (DLQ)

Each queue has a DLQ: `<queue>.dlq`. DLQ messages are not auto-retried. They require manual intervention:

- The UI shows DLQ depth per queue (admin-only).
- An admin can replay a DLQ message (re-publish to the original queue with `attempt_count: 1`) or discard it (with audit).
- DLQ messages older than 30 days are auto-archived to PostgreSQL (`dlq_archive` table) and dropped from RabbitMQ.

DLQ events trigger an alert (per `OBSERVABILITY.md`).

## 7. Queue catalog

### `email.sync`
- **Producer**: API (webhook handlers), scheduled poller
- **Consumer**: `worker.email-sync`
- **Payload**: `{ account_id: uuid, history_id?: string, refresh?: boolean }`
- **Idempotency**: `{account_id}:{history_id or 'full'}`
- **Max attempts**: 5
- **Failure handling**: if account is revoked, set `email_accounts.status='revoked'`, ack message. If token expired, set `status='expired'`, enqueue refresh task.

### `email.parse`
- **Producer**: `email.sync` consumer
- **Consumer**: `worker.email-parse`
- **Payload**: `{ message_id: uuid }`
- **Idempotency**: `{message_id}`
- **Max attempts**: 5
- **Failure handling**: parse failures are usually permanent (malformed MIME). After 5 attempts, DLQ + mark `email_messages.embedding_status='failed'`.

### `email.index`
- **Producer**: `email.parse` consumer
- **Consumer**: `worker.email-index` (uses Clara's `knowledge-bases/core/embedding-index.ts`)
- **Payload**: `{ message_id: uuid }`
- **Idempotency**: `{message_id}`
- **Max attempts**: 5
- **Failure handling**: if embedding provider fails, retry with backoff. After 5 attempts, DLQ + mark `embedding_status='failed'`. The message is still searchable via full-text search (tsvector).

### `email.attachments`
- **Producer**: `email.parse` consumer
- **Consumer**: `worker.email-attachments`
- **Payload**: `{ message_id: uuid, attachment_id: uuid }`
- **Idempotency**: `{message_id}:{attachment_id}`
- **Max attempts**: 5
- **Failure handling**: storage failures (Supabase Storage) are retried. Virus-scan failures (ClamAV unavailable) are retried up to 3 times, then marked `virus_scan_status='skipped'` and flagged for manual review.

### `email.classify`
- **Producer**: `email.parse` consumer
- **Consumer**: `worker.email-classify` (uses agent runtime in classify-only mode)
- **Payload**: `{ message_id: uuid }`
- **Idempotency**: `{message_id}`
- **Max attempts**: 3 (classification is best-effort; failure does not block search)

### `email.draft`
- **Producer**: agent runtime (when intent is `draft_email` or `draft_reply`)
- **Consumer**: `worker.email-draft`
- **Payload**: `{ agent_id: uuid, account_id: uuid, draft_params: object, conversation_id: uuid, turn_id: uuid }`
- **Idempotency**: `{agent_id}:{draft_request_hash}`
- **Max attempts**: 5

### `email.send`
- **Producer**: agent runtime (after authorization for `send_email`)
- **Consumer**: `worker.email-send`
- **Payload**: `{ action_id: uuid, draft_id: uuid or send_params }`
- **Idempotency**: `{action_id}` — strictly one send per approved action
- **Max attempts**: 5
- **Failure handling**: provider 5xx retried. Provider 4xx (invalid recipient, etc.) not retried; audit; surface to user.

### `email.action`
- **Producer**: agent runtime (for bulk modify, delete, forward after authorization)
- **Consumer**: `worker.email-action`
- **Payload**: `{ action_id: uuid }`
- **Idempotency**: `{action_id}`
- **Max attempts**: 5

### `whatsapp.inbound`
- **Producer**: API webhook handler
- **Consumer**: `worker.whatsapp-inbound`
- **Payload**: `{ whatsapp_account_id: uuid, provider_event_id: string, raw_event: object }`
- **Idempotency**: `{provider_event_id}`
- **Max attempts**: 5

### `whatsapp.outbound`
- **Producer**: agent runtime (reply), scheduled job, automation
- **Consumer**: `worker.whatsapp-outbound`
- **Payload**: `{ agent_id: uuid, contact_phone: string, message: object, conversation_id?: uuid }`
- **Idempotency**: `{agent_id}:{contact_phone}:{request_hash}`
- **Max attempts**: 5
- **Failure handling**: 4xx (template required, invalid contact) not retried. 5xx retried. Rate-limit (429) pauses the queue for the number's window.

### `agent.schedule`
- **Producer**: cron loop (per scheduled_jobs)
- **Consumer**: `worker.agent-schedule`
- **Payload**: `{ scheduled_job_id: uuid, fire_at: string }`
- **Idempotency**: `{scheduled_job_id}:{fire_at}` — strictly one execution per fire
- **Max attempts**: 3 (if a scheduled job fails 3x, mark `scheduled_jobs.status='error'` and notify user)

### `agent.execute`
- **Producer**: `agent.schedule` consumer, WhatsApp inbound, automation rule
- **Consumer**: `worker.agent-execute`
- **Payload**: `{ agent_id: uuid, conversation_id: uuid, turn_id: uuid, request: AgentRequest }`
- **Idempotency**: `{conversation_id}:{turn_id}`
- **Max attempts**: 3

### `summary.generate`
- **Producer**: agent runtime (intent `summarize_emails`), scheduled job
- **Consumer**: `worker.summary-generate`
- **Payload**: `{ agent_id: uuid, scope: string, period_start: string, period_end: string, conversation_id?: uuid }`
- **Idempotency**: `{agent_id}:{scope}:{period_start}:{period_end}`
- **Max attempts**: 3

### `embedding.generate`
- **Producer**: `email.index`, KB ingest
- **Consumer**: `worker.embedding-generate` (uses Clara's `ai-core/multilingual-embeddings.ts`)
- **Payload**: `{ source_type: 'email'|'kb', source_id: uuid, model: string }`
- **Idempotency**: `{source_type}:{source_id}:{model}`
- **Max attempts**: 5

### `voice.telemetry`
- **Producer**: API `/api/voice/turn` handler
- **Consumer**: `worker.voice-telemetry`
- **Payload**: `{ voice_session_id: uuid, turn_id: uuid, stage: string, latency_ms: number, provider_metadata: object }`
- **Idempotency**: `{voice_session_id}:{turn_id}:{stage}`
- **Max attempts**: 2 (best-effort — telemetry loss is acceptable)

### `audit.persist`
- **Producer**: every API route and every worker (after a successful or failed operation)
- **Consumer**: `worker.audit-persist`
- **Payload**: `{ audit_event: AuditEvent }`
- **Idempotency**: `{audit_event_id}`
- **Max attempts**: 10 (audit is critical — must not be lost)
- **Failure handling**: if persist fails 10x, write to a local file-based fallback on the worker host and alert. The file-based fallback is replayed on recovery.

## 8. Correlation IDs

Every message has a `correlation_id`. Producers set it from the originating request:

- Webhook-triggered: `correlation_id = provider_event_id` (or UUID if none)
- User-requested: `correlation_id = request_id` (from API)
- Scheduled: `correlation_id = '{scheduled_job_id}:{fire_at}'`
- Voice: `correlation_id = voice_session_id`

The `correlation_id` is propagated to `audit_events.correlation_id`, enabling end-to-end tracing from request → queue → worker → audit.

## 9. Observability

Per queue, we track:

- Depth (gauge)
- Publish rate (counter)
- Ack rate (counter)
- Nack rate (counter)
- DLQ depth (gauge)
- Consumer latency (histogram)
- Retry rate (counter)

Per message, we track:

- Time in queue (enqueued_at → acked_at)
- Attempt count at ack
- Whether it ended in DLQ

These metrics are emitted to the observability stack (see `OBSERVABILITY.md`). Alerts fire on:

- DLQ depth > 0 (warn) or > threshold (critical)
- Queue depth growing (consumer lag)
- Ack rate < publish rate sustained (consumer stalled)
- Retry rate > 10% of ack rate

---

## 10. Recovery

RabbitMQ is **not** authoritative. Recovery procedures:

- **RabbitMQ lost**: rebuild from PostgreSQL state. Sync cursors restart from last-known `history_id`. Scheduled jobs re-fire from `next_fire_at`. In-flight messages are lost; producers re-emit on next webhook/poll.
- **Worker host lost**: messages accumulate in RabbitMQ (within disk budget). When workers return, they drain the backlog.
- **Redis lost**: idempotency dedup is lost — consumers may reprocess recent messages. Idempotency at the application layer (database constraints, e.g., unique `provider_message_id`) catches duplicates. Rate-limit counters reset — brief burst possible.

These recovery properties are validated in Phase 17 (observability + audit + security hardening) and Phase 18 (end-to-end testing).
